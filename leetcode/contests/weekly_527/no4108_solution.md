# [Python3] 4108. 使红色节点连通的最小代价：一次 DFS，先算全蓝账，再找最大节省

**先把所有红点变蓝的费用作为基准，再用树形 DP 找一个收益最大的红色连通块。红点保留下来能省钱，蓝点加入需要花钱，最终答案就是“全蓝费用 − 最大节省”。**

一次 DFS 同时计算子树大小和最大收益，时间复杂度 `O(n)`，空间复杂度 `O(n)`。

## 1. 先上完整解法：两笔账，别混在一起

```python
from typing import List
class Solution:
    def minCost(self, n: int, colors: str, edges: List[List[int]]) -> int:
        g = [[] for _ in range(n)]
        for u, v in edges:
            g[u].append(v)
            g[v].append(u)
        cost_all_blue = 0
        max_saving = 0

        def dfs(u, parent):
            nonlocal cost_all_blue, max_saving
            size = 1
            saving = 0
            for v in g[u]:
                if v == parent:
                    continue
                child_size, child_saving = dfs(v, u)
                size += child_size
                saving += max(0, child_saving)

            if colors[u] == 'R':
                cost_all_blue += size
                saving += size
            else:
                saving -= size
            max_saving = max(max_saving, saving)
            return size, saving
        dfs(0, -1)
        return cost_all_blue - max_saving
```

先给变量贴上具体含义：

| 变量 | 它到底在算什么 |
| --- | --- |
| `size` | 当前节点的完整子树大小，也是翻转当前节点的价格 |
| `cost_all_blue` | 把所有原始红点变蓝的总费用 |
| `saving` | 在当前子树里，保留一个必须包含当前节点的红色连通块，最多能省多少钱 |
| `max_saving` | 比较所有节点的候选方案，得到的最大节省 |

这道题让我最容易卡住的地方，是看见 `cost_all_blue` 和 `saving` 同时增加，就以为程序在给同一笔钱开两张发票。

实际上，一笔是基准预算，另一笔是修改方案后省下的钱。它们最后要相减。

## 2. 先明确：翻转的是一个节点，收费标准是子树大小

树以 `0` 为根。翻转节点 `u`，只改变 `u` 自己的颜色，代价等于它的子树大小。

例如，某个蓝点的子树一共有 `4` 个节点，把它变红要花 `4`。下面三个节点的颜色不会跟着改变。

看到“子树大小”，很容易顺手理解成“整棵子树一起变色”。收费按整桌算，实际只给一个人换衣服，这个区别必须先弄清楚。

目标是让所有红点连成一块；蓝点不需要连通，没有红点也合法。因此，我们可以把最终状态理解成：

> 选择一个连通块，让里面全红，外面全蓝；这个连通块允许为空。

这块红色区域可以舍弃一些分支，也可以完全不包含根节点 `0`。

## 3. 全变蓝的费用，到底在哪儿算？

就在原代码这句：`cost_all_blue += size`。

执行它的条件是当前节点原本为红色。DFS 会访问每个节点，所以最终累加的就是：

```text
cost_all_blue = 所有原始红点的子树大小之和
```

原本为蓝色的节点不需要操作，因此不会往这笔基准费用里加钱。

为什么选全蓝作为基准？因为它一定合法，而且费用很好计算。全蓝方案仅用于比较费用，不需要真的先把红点全部翻蓝，再翻回来。

注意：累加这笔费用时使用的是 `size`，它已经包含所有孩子的子树大小。因此，这段逻辑必须放在处理完所有孩子之后。

## 4. 红点加 size，蓝点减 size，是怎么来的？

我们已经算出了全部变蓝要花的钱。现在改主意，选择一块区域保留为红色。

对于一个进入最终红色连通块的节点：

| 原始颜色 | 全蓝基准方案 | 现在的方案 | 相比基准的节省 |
| --- | --- | --- | --- |
| 红色 | 花 `size` 把它变蓝 | 保持红色，不翻转 | `+size` |
| 蓝色 | 保持蓝色，不花钱 | 花 `size` 把它变红 | `-size` |

所以原代码中：

- `saving += size`：红点留下来，省掉原本要付的翻转费用。
- `saving -= size`：蓝点要加入连通块，额外支付变红费用。

例如，孩子提供的红色连通块能省 `6`，但当前节点是蓝色，变红要花 `4`。

```text
孩子带来的节省：  +6
当前蓝点变红：    -4
最终净节省：      2
```

`saving` 是“省了多少钱”，所以额外花钱要做减法。它可能为负数，表示这个方案相比全蓝基准更贵。

## 5. dfs 返回什么？必须先把“包含当前节点”读出来

`dfs(u, parent)` 返回 `(size, saving)`：

1. `size` 是以 `u` 为根的完整子树大小。
2. `saving` 是在这棵子树中，选择一个**必须包含 `u`** 的红色连通块的最大收益。

“必须包含 `u`”是保证连通性的关键。

如果父节点想接入这个孩子提供的红色连通块，就要经过父子之间的边。孩子返回的连通块包含孩子自己，父节点才能直接把它接上来。

例如：

```text
父节点 u
└── 孩子 v
    └── 更下面的节点 x
```

如果只说“下面有一块很划算的红点”，却允许跳过 `v`，父节点就没法保证连得过去。不能只把目的地涂红，指望中间的蓝点自动修桥。

## 6. 为什么对子树取 max(0, child_saving)？

对于孩子 `v`，有两个选择：

- 接入包含 `v` 的最佳红色连通块，收益为 `child_saving`。
- 舍弃这个分支，收益为 `0`。

因此，原代码写成：`saving += max(0, child_saving)`。

收益大于 `0` 就接上，小于 `0` 就舍弃，等于 `0` 时任选。

舍弃分支时，里面的原始红点需要变蓝。这笔钱已经包含在 `cost_all_blue` 中，所以这里不需要重复加费用。

不同孩子的选择可以分别计算，因为被选中的孩子连通块都通过 `u` 连在一起。

如果用公式写，设 `weight[u]` 为红点的 `+size[u]` 或蓝点的 `-size[u]`，就有：

```text
saving[u] = weight[u] + 所有孩子的 max(0, saving[v]) 之和
```

## 7. 用一个七节点例子，把递归完整走一遍

括号中是子树大小，也就是翻转当前节点的价格：

```text
0 红（7）
├── 1 蓝（4）
│   └── 2 红（3）
│       └── 3 红（2）
│           └── 4 红（1）
└── 5 蓝（2）
    └── 6 红（1）
```

原始红点是 `0、2、3、4、6`，所以全蓝费用为：

```text
7 + 3 + 2 + 1 + 1 = 14
```

按图中的孩子顺序遍历，DFS 从叶子向上返回：

| 当前节点 | `size` | 孩子贡献的正收益 | 当前节点自身收益 | 返回的 `saving` |
| --- | --- | --- | --- | --- |
| 4 红 | 1 | 0 | +1 | 1 |
| 3 红 | 2 | 1 | +2 | 3 |
| 2 红 | 3 | 3 | +3 | 6 |
| 1 蓝 | 4 | 6 | -4 | 2 |
| 6 红 | 1 | 0 | +1 | 1 |
| 5 蓝 | 2 | 1 | -2 | -1 |
| 0 红 | 7 | 2 + 0 | +7 | 9 |

根节点 `0` 收到两个孩子的结果：

- 节点 `1` 返回收益 `2`：把蓝点 `1` 变红要花 `4`，但能保留的红点省下 `6`，值得接上。
- 节点 `5` 返回收益 `-1`：把蓝点 `5` 变红要花 `2`，却只能省下红点 `6` 的 `1`，舍弃这个分支。

最终：

```text
全蓝费用 = 14
最大节省 = 9
最小代价 = 14 - 9 = 5
```

实际操作只有两次：节点 `1` 变红花 `4`，节点 `6` 变蓝花 `1`，合计 `5`。

这也说明，只想着连接所有原始红点会漏掉更优方案。有时让一个偏远红点变蓝，比修一条蓝点变红的连接路线便宜。

## 8. 为什么要记录 max_saving，不能只拿根节点的 saving？

因为 `dfs(0, -1)` 返回的 `saving` 要求连通块包含根节点 `0`。

但最终红色连通块可以只在某个孩子的子树里，所以每个节点算出的结果都要参与比较：`max_saving = max(max_saving, saving)`。

看一个更小的反例：

```text
0 蓝（3）
└── 1 红（2）
    └── 2 红（1）
```

两个红点本来就连通，正确答案是 `0`。

```text
cost_all_blue = 2 + 1 = 3
节点 1 的 saving = 2 + 1 = 3
节点 0 的 saving = -3 + 3 = 0
```

如果只用根节点的收益，就会算出 `3 - 0 = 3`。记录全局最大收益后，得到 `3 - 3 = 0`，对应直接保留节点 `1、2`。

`max_saving` 从 `0` 开始，则同时考虑了“不保留任何红点”的情况。

## 11. 刷这道题时，我会提醒自己避开的坑

**坑一：把“所有红点连通”写成“整棵子树全红”。**

红根连接一个蓝叶时，只有一个红点，本来就合法。如果要求每个孩子子树都全红，就把原本合法的蓝色分支也算成了问题。

**坑二：size 也只加有收益的孩子。**

`size += child_size` 必须对每个孩子执行。翻转价格由固定的整棵子树决定，不能因为不想保留某个分支，就让它从收费面积里消失。

**坑三：把负数 saving 当成计算错误。**

原代码保留“必须包含当前节点”的收益，允许它为负数；父节点通过 `max(0, child_saving)` 决定是否接入。这样每个返回值的含义始终一致。

**坑四：以为 cost_all_blue 在执行翻转。**

它只在累计基准费用，没有修改 `colors`。对原始红点计算变蓝费用，再统计保留它能省的钱，最后相减，不会真的把同一个节点翻来覆去收费。

**坑五：想用 lru_cache 处理递归太深。**

这里每个节点只计算一次，没有重复子问题需要缓存。缓存不会降低一条长链的调用深度。递归版需要设置足够的递归深度；要避免递归调用，则可以改为显式栈遍历。

## 12. 为什么这个 DP 覆盖了所有方案？

任意非空红色连通块，都有唯一的、深度最小的节点 `u`。整个连通块位于 `u` 的子树中，并且包含 `u`。

对于 `u` 的任意孩子 `v`：如果连通块进入这个分支，就必须经过 `v`，因此在分支内选择的也是一个包含 `v` 的连通块；如果不进入，就舍弃这个分支。

DFS 恰好枚举了这两种选择，并为每个分支选出更大的收益，所以得到了包含 `u` 的最佳方案。再比较所有节点的结果，并加入空连通块的收益 `0`，就覆盖了全部合法方案。

每个节点处理一次，每条边只检查常数次，时间复杂度为 `O(n)`。邻接表与递归栈占用 `O(n)` 空间。

两份原代码均已通过六组固定用例，以及 900 组随机小树与穷举最终颜色集合的对照验证。十八节点例子额外枚举了全部 `2^18` 种最终颜色集合，确认最小代价为 `15`；补充递归深度设置后，两份代码也通过了十万节点全红长链和全蓝长链测试。

这题最值得带走的思路是：**先找一个费用容易计算的合法方案，再把每一次改变换算成收益，用 DP 求最大节省。** 两笔账的含义写清楚以后，那句 `saving -= size` 就有了具体的来历。
