# [Python3] 两个堆安排服务器：从 heapq 入门到双堆模板，时钟终于不用逐秒加班了

**做法：空闲服务器用 `(权重, 下标)` 的小根堆维护，忙碌服务器用 `(完成时间, 下标)` 的小根堆维护。分配任务前先释放所有已经完成任务的服务器；没有空闲服务器时，把时间直接跳到下一次完成任务的时刻。**

这道 [1882. 使用服务器处理任务](https://leetcode.cn/problems/process-tasks-using-servers/description/) 很适合把 `heapq` 的基本用法、元组排序和双堆调度串起来学习。下面先放 Jupyter 中的完整实现，代码原样保留。

设服务器数量为 `n`，任务数量为 `m`。时间复杂度为 `O(n + m log(n + 1))`；不计返回数组，额外空间为 `O(n)`。

## 1. 先上完整代码：两张名单，各管各的

```python
from typing import List
import heapq
class Solution:
    def assignTasks(self, servers: List[int], tasks: List[int]) -> List[int]:
        idle_servers = [(w,idx) for idx,w in enumerate(servers)]
        heapq.heapify(idle_servers)
        busy_servers = []

        ans = []
        ts = 0
        def release():
            while busy_servers and busy_servers[0][0]<=ts:
                end_time, idx = heapq.heappop(busy_servers)
                heapq.heappush(idle_servers,(servers[idx],idx))

        for idx,task in enumerate(tasks):
            ts = max(idx,ts)
            release()
            if not idle_servers:
                ts = busy_servers[0][0]
                release()

            weight, idx = heapq.heappop(idle_servers)
            ans.append(idx)
            heapq.heappush(busy_servers,(ts+task,idx))


        return ans
```

先记住这两个问题，后面的代码就有了方向：

> 空闲时，谁最适合接任务？忙碌时，谁最早能回来？

前者看权重和下标，后者看完成时间。它们使用不同的排序规则，所以准备两个堆。

## 2. 先把题目翻译成人话

`servers[i]` 是服务器 `i` 的权重，`tasks[j]` 是任务 `j` 需要运行多久。

分配规则是：

1. 任务 `j` 在第 `j` 秒到达，不能提前处理。
2. 任务按照下标顺序分配，后来的任务不能插队。
3. 有空闲服务器时，选权重最小的；权重相同，选下标最小的。
4. 没有空闲服务器时，等到最早有人完成，再继续分配。

权重只决定“空闲时优先选谁”，不影响运行速度。任务耗时是 `tasks[j]`，不能因为服务器权重小，就给它偷偷安装加速器。

## 3. heapq 到底替我们做了什么？

堆适合这样的需求：**集合里的元素不断增加、删除，而我反复只想取最小的那个。**

Python 的 `heapq` 默认提供小根堆，可以用普通列表保存。关键操作如下，行为与复杂度可参考 [Python 官方 heapq 文档](https://docs.python.org/3/library/heapq.html)。

| 写法 | 作用 | 时间复杂度 |
| --- | --- | --- |
| `heapq.heapify(heap)` | 把已有列表调整成小根堆，原地修改 | `O(k)` |
| `heap[0]` | 查看最小元素，不删除 | `O(1)` |
| `heapq.heappush(heap, x)` | 加入元素，并维护堆结构 | `O(log(k + 1))` |
| `heapq.heappop(heap)` | 删除并返回最小元素，维护堆结构 | `O(log(k + 1))` |

这里 `k` 是堆中元素的数量。`heappop` 要求堆非空。

先看一个能直接运行的小例子：

```python
import heapq

heap = [5, 2, 8]
heapq.heapify(heap)

print(heap[0])                # 2，只看，不删除
heapq.heappush(heap, 1)       # 加入 1
print(heapq.heappop(heap))    # 1，取走最小值
print(heapq.heappop(heap))    # 2，现在的最小值
```

**堆只保证堆顶最小，不保证整个列表已经排好序。** 不要看见变量叫 `heap`，就以为它已经拿到了全员有序的资格证。

维护堆时，加入元素用 `heappush`；取最小元素用 `heappop`。

## 4. 一份可以复用的堆排序模板

把所有元素建成小根堆，再依次弹出最小值，就能得到升序结果：

```python
import heapq


def heap_sort(nums):
    # 复制一份，避免 heapify 和后面的弹出操作修改输入。
    heap = list(nums)
    heapq.heapify(heap)

    ordered = []
    while heap:
        ordered.append(heapq.heappop(heap))

    return ordered


print(heap_sort([5, 2, 8, 1, 2]))  # [1, 2, 2, 5, 8]
```

长度为 `k` 时，建堆用时 `O(k)`，全部弹出用时 `O(k log(k + 1))`，额外空间为 `O(k)`。

这是借助额外堆空间实现的排序写法。1882 在此基础上继续维护动态变化的服务器集合，适合作为**双堆／优先队列调度模板题**。

## 5. 元组放进堆里，为什么就能按两条规则排序？

元组按从左到右的顺序比较：先比较第一项，第一项相同才比较第二项。

例如：

```python
import heapq

idle = [(3, 0), (3, 1), (2, 2)]
heapq.heapify(idle)

print(heapq.heappop(idle))  # (2, 2)：权重更小
print(heapq.heappop(idle))  # (3, 0)：权重相同，下标更小
print(heapq.heappop(idle))  # (3, 1)
```

所以本题的空闲堆写成：

```text
idle_servers：保存 (权重, 服务器下标)
```

堆顶就是当前最应该接任务的服务器。

忙碌堆写成：

```text
busy_servers：保存 (完成时间, 服务器下标)
```

堆顶就是最早完成任务的服务器。

忙碌堆的第二项只用于区分服务器，并在完成时间相同时确定弹出顺序。**它不负责决定下一项任务交给谁**，真正的选择发生在空闲堆。

## 6. 顺着原代码，读懂每一步

### 初始化：所有服务器都空闲

`idle_servers = [(w,idx) for idx,w in enumerate(servers)]` 为每台服务器建立 `(权重, 下标)`。

随后调用 `heapify`，让堆顶符合“权重优先、下标次之”的规则。此时还没有任务运行，所以 `busy_servers` 为空。

### ts：我们现在走到了哪一秒？

`ts` 是当前调度时间。处理任务前执行：

```text
ts = max(任务到达时间, 当前时间)
```

在原代码里，任务到达时间就是外层 `enumerate(tasks)` 得到的 `idx`。

为什么取最大值？

- 如果之前的任务没有让我们等待，就等到当前任务到达。
- 如果之前已经等到了更晚的时间，就继续使用这个时间，不能把时钟拨回去。

例如某任务在第 `2` 秒到达，但服务器一直忙到第 `10` 秒，下一项任务在第 `3` 秒到达。轮到它时，时间仍然是第 `10` 秒。

原实现里的 `idx` 会在弹出空闲服务器后被改成服务器下标。下一轮循环时，`enumerate` 会重新为它赋值为任务下标。这种复用可以运行；读代码时要注意同名变量在前后两处的含义。

### release：把已完成的服务器全部放回空闲堆

释放条件是：

```text
忙碌堆非空，并且最早完成时间 <= 当前时间 ts
```

满足条件时，从忙碌堆弹出服务器，再以 `(权重, 下标)` 的形式放回空闲堆。

`<=` 表示服务器恰好在当前时刻完成，也可以立刻接下一项任务，不需要再休息一秒。

这里必须使用 `while`。可能有多台服务器同时完成，也可能时间推进后有多台早已完成。它们都应进入本轮候选名单。

原代码的 `release()` 只读取外层的 `ts`，没有给 `ts` 重新赋值，所以不需要写 `nonlocal ts`。

### 没有空闲服务器：直接跳到下一次完成时刻

执行第一次 `release()` 后，如果空闲堆仍然为空，就等待最早完成任务的服务器：

```text
ts = busy_servers[0][0]
```

然后再次调用 `release()`，释放截至这个新时刻的所有已完成服务器。

服务器没空的时候，逐秒执行 `ts += 1` 也改变不了现实。它要忙到第十万秒，我们就直接翻到第十万秒，时钟不用逐秒打卡。

题目至少有一台服务器，每台服务器始终在两个堆中的一个里。因此，空闲堆为空时，忙碌堆一定非空，可以读取它的堆顶。

### 分配任务：从空闲堆拿一个，再放进忙碌堆

此时空闲堆已经包含当前所有可用服务器。

从中弹出最小的 `(权重, 下标)`，把服务器下标加入答案，再将它放入忙碌堆：

```text
完成时间 = 实际开始时间 ts + 任务耗时 task
```

注意，开始时间使用 `ts`。任务如果排队等过了，就不能仍然使用它的到达时间。

## 7. 用 Jupyter 中的例子走一遍

```python
servers = [3,3,2]
tasks = [1,2,3,2,1,2]
solution = Solution()

print(result)
```

输出为：

```text

```

服务器权重为 `[3, 3, 2]`，所以在服务器都空闲时，优先级是 `2 → 0 → 1`。

| 任务下标 | 到达时间 | 实际开始时间 | 释放后可用的服务器下标集合 | 选择 | 完成时间 |
| --- | --- | --- | --- | --- | --- |
| 0 | 0 | 0 | `{0, 1, 2}` | 2 | 1 |
| 1 | 1 | 1 | `{0, 1, 2}` | 2 | 3 |
| 2 | 2 | 2 | `{0, 1}` | 0 | 5 |
| 3 | 3 | 3 | `{1, 2}` | 2 | 5 |
| 4 | 4 | 4 | `{1}` | 1 | 5 |
| 5 | 5 | 5 | `{0, 1, 2}` | 2 | 7 |

这个例子中，第 `5` 秒三台服务器同时完成。先全部释放，再按权重选出服务器 `2`。

## 8. 最值得防的坑：谁先弹出，谁就先上班？

看这个补充例子：

```text
servers = [10, 1]
tasks   = [5, 4, 1]
```

过程如下：

- 第 `0` 秒，任务 `0` 交给服务器 `1`，第 `5` 秒完成。
- 第 `1` 秒，任务 `1` 交给服务器 `0`，也在第 `5` 秒完成。
- 第 `2` 秒，任务 `2` 到达，但没有空闲服务器，要等到第 `5` 秒。

这时忙碌堆中是：

```text
(5, 0)、(5, 1)
```

如果只弹出一个服务器就立即分配任务，会选到服务器 `0`。但两台都在第 `5` 秒空闲，应该按权重选服务器 `1`。

正确答案是：

```text
[1, 0, 1]
```

所以原代码的顺序非常重要：

```text
跳到最早完成时刻
→ 释放所有完成时间 <= 当前时刻的服务器
→ 从空闲堆里按权重、下标选择
```

忙碌堆负责报“谁下班了”，空闲堆负责决定“谁接着干”。不能因为服务器 `0` 在忙碌堆里先被叫到，就顺手给它派活。

另外几个容易写错的地方：

| 容易写错的地方 | 应该怎么处理 |
| --- | --- |
| 把 `release` 的 `while` 写成 `if` | 一次释放所有已经完成的服务器 |
| 完成时间用 `< ts` | 用 `<= ts`，当前时刻完成也能立即接任务 |
| 每个任务都令 `ts = 任务下标` | 使用 `max`，调度时间不能倒退 |
| 完成时间写成“到达时间 + 耗时” | 使用“实际开始时间 + 耗时” |
| 堆里只保存权重 | 加上下标，处理权重相同的情况 |

## 9. 为什么不需要再写一个等待任务队列？

任务按下标顺序到达，题目也要求等待任务按下标顺序分配。因此，直接按 `tasks` 的顺序遍历，就是在处理队头任务。

如果发生等待，`ts` 会向前跳。下一轮到达时间仍不超过 `ts` 时，就可以在同一时刻继续分配下一项任务。

外层 `for` 每次分配一项任务，但不代表每次必须过去一秒。只要服务器足够空闲，多个积压任务可以具有相同的开始时间。

## 10. 留下一份可迁移的双堆调度模板

遇到“资源有选择优先级、使用后被占用、到某个时刻恢复可用”的问题，可以按下面的顺序组织代码：

```text
建立空闲堆：按资源的选择优先级排序
建立忙碌堆：按资源恢复可用的时间排序

按照题目规定的顺序遍历任务：
    当前时间 = max(当前时间, 任务到达时间)
    释放所有恢复时间 <= 当前时间的资源

    如果没有空闲资源：
        当前时间 = 最早的资源恢复时间
        再次释放所有恢复时间 <= 当前时间的资源

    从空闲堆取最优资源
    记录分配结果
    计算资源恢复时间，放入忙碌堆
```

本题把模板填成：

| 模板位置 | 1882 中填写的内容 |
| --- | --- |
| 任务顺序 | 按任务下标递增 |
| 任务到达时间 | 任务下标 |
| 空闲资源优先级 | `(权重, 服务器下标)` |
| 资源恢复时间 | `ts + task` |
| 忙碌堆元素 | `(完成时间, 服务器下标)` |
| 没有资源时怎么办 | 时间跳到最早完成时刻 |

这个模板适用于任务处理顺序已经确定、资源选择规则也明确的调度。换题时，如果任务也有动态优先级，还需要另外维护等待任务的选择规则。

## 11. 为什么 release 里有 while，整体仍然很快？

每项任务分配时：

- 从空闲堆弹出一台服务器。
- 向忙碌堆加入一条记录。

这条忙碌记录以后最多被释放一次，再放回空闲堆。

所以虽然 `release()` 在外层循环中被反复调用，但所有调用累计弹出的忙碌记录不会超过 `m` 条。最后仍在运行的记录甚至不需要弹出。

初始化空闲堆需要 `O(n)`；两个堆的大小都不超过 `n`，总共执行 `O(m)` 次堆操作，因此总时间为：

```text
O(n + m log(n + 1))
```

两个堆合计维护 `n` 台服务器，额外空间为 `O(n)`；答案数组占 `O(m)`，计入返回结果时总空间为 `O(n + m)`。
